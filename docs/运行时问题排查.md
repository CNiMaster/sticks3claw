背景：程序能编译通过但实机「总出问题」。以下逐条记录审查到的运行时缺陷、
修复方式与**为什么原来的写法会出错**。

## 修复清单

### 1. STT 回调注册太晚，早期错误要等到超时才暴露

**现象**：火山引擎 Token 填错时，设备要卡满十几秒才提示失败，用户以为死机。

**原因**：`ws.onEvent(...)` 原本在**发完所有音频之后**才注册。连接握手和发音频期间
（可达数秒）服务器若已返回鉴权错误，因为回调没注册，程序收不到，只能干等响应超时。

**修复**：把 `onEvent` 移到 `ws.beginSSL()` **之前**注册，并补充 `WStype_DISCONNECTED`
处理（连接被服务端断开时立刻结束等待，而不是继续空转）。

`src/stt/volcengine_stt.cpp`

### 2. 发送音频期间不驱动 WebSocket 状态机

**现象**：长录音识别结果不完整，或服务端中途报错收不到。

**原因**：发音频的循环里只有 `delay(10)`，没有 `ws.loop()`。WebSocket 是双向流——
要真正把缓冲里的数据发出去、以及处理服务端在收音频过程中就返回的中间响应，
都必须靠 `ws.loop()` 驱动。

**修复**：每个音频包发送后补 `ws.loop()`。

`src/stt/volcengine_stt.cpp`

### 3. 等待 AI 回复时设备会熄屏 / 休眠，流程中断

**现象**：说完话等 AI 回复，屏幕黑掉，甚至再也收不到回复。

**原因**：`PowerManager::update()` **完全不感知业务状态**，只按空闲计时判断。
`SCREEN_OFF_TIMEOUT_MS` 是 30 秒，而 AI 请求超时原本设的也是 30 秒——
一次稍慢的 AI 请求就足以让设备在等待期间熄屏，进而走向 light sleep：
light sleep 会 **断开 WiFi**，流程直接断掉。

**修复**：给 `PowerManager` 增加 `setBusy(bool)`。业务忙（录音 / 识别 / 等待 AI /
播放）期间 `update()` 直接返回，跳过一切省电动作。
接入点：`startRecording()`、进入 `WAITING_REPLY` 时置 busy，`returnToIdle()` 解除。
busy 解除时刷新活动计时，避免刚干完活立刻熄屏。

`src/system/power_manager.{h,cpp}`、`src/sticks3claw.cpp`

### 4. MQTT 模式下永远等不到回复会卡死

**现象**：OpenClaw 没开或 Broker 不可达时，设备永远停在「Waiting...」，
既不说话也不休眠，按键之外无任何反应。

**原因**：`sendTextToAI()` 在 MQTT 分支发出消息后设 `WAITING_REPLY`，
之后**只靠收到 MQTT 消息**才会回到 IDLE。没有任何超时兜底。

**修复**：新增 `MQTT_REPLY_TIMEOUT_MS`（30 秒）。loop 中检测等待超时则提示
`Timeout` 并 `returnToIdle()`。

`src/sticks3claw.cpp`

### 5. AI 请求超时过长，期间屏幕完全不刷新

**现象**：服务器慢时，设备几十秒无任何反应，用户判定为死机。

**原因**：整条链路（STT → AI → TTS）是**同步阻塞**的，AI 请求期间 loop 不执行，
屏幕不刷新。原超时 `http.setTimeout(30000)` 意味着最长 30 秒黑屏式等待。

**修复**：`setTimeout` 30s → 15s，`setConnectTimeout` 10s → 8s。
正常响应在数秒内，15 秒足够覆盖慢速模型；失败则快速报错让用户重试，
比让用户盯着无响应的设备 30 秒体验好得多。

`src/communication/ai_client.cpp`

## 已核实**不是**问题的项（勿再改）

排查时逐一验证过，避免重复踩坑：

| 项 | 结论 |
|---|---|
| I2S 引脚映射 | `data_out_num = I2S_DIN_PIN`（ESP32→ES8311）、`data_in_num = I2S_DOUT_PIN`（ES8311→ESP32）**方向正确** |
| I2S DMA 缓冲 | `dma_buf_count=8 × dma_buf_len=1024` = 8KB ≈ 128ms 缓冲，loop 周期远小于此，**不会丢数据** |
| 录音缓冲 | 512KB（≈16s @16kHz/16bit/mono）> `RECORDING_TIMEOUT_MS` 10s，够用 |
| `stereoBuf[2048]` 栈缓冲 | 有 `stereoLen > sizeof(stereoBuf)` 保护，**不会溢出** |
| WiFi 自动重连 | `WiFiManager::update()` 按 `RECONNECT_INTERVAL` 重试，且监听 `WIFI_STA_DISCONNECTED` 事件，逻辑正确 |
| MQTT 自动重连 | `MQTTClient::update()` 按 `MQTT_RECONNECT_INTERVAL` 重试，正确 |
| light sleep 唤醒 | ext1 + `ESP_EXT1_WAKEUP_ANY_LOW`（KEY1/KEY2），唤醒后重连 WiFi/MQTT，正确 |

## 复现验证命令

```bash
cd /Users/master/Project/sticks3claw
pio run                    # 编译，应 SUCCESS 且 0 error
pio run --target upload    # 烧录
pio device monitor -b 115200   # 看串口日志
```

关注的串口输出：

- `Init done!` —— 初始化完成
- `IP: x.x.x.x` —— 联网成功
- `STT API error: code=...` —— 凭证错误，检查 `env/secrets.h`
- `MQTT reply timeout` —— OpenClaw 未运行或 Broker 地址不对
- `Power: state=... idle=...` —— 每 60 秒打印电源状态，可确认是否误休眠
